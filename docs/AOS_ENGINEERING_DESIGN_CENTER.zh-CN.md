# AOS 研发方案设计中心

## 定位

AOS 研发模块的第一阶段聚焦高质量工程设计：把业务需求、真实代码仓库和团队约束整理成可以审查、下载并交给外部 Code Agent 执行的工程方案。

它的交付标准不是“生成一段看起来合理的文字”，而是让另一个工程 Agent 能在没有口头补充的情况下开始实施，并且知道边界、风险和验收方式。

## 设计流水线

```text
需求输入 -> 澄清 -> 需求方案 -> 仓库事实 -> 代码研发方案
       -> 架构/API/数据/权限/安全 -> 任务拆解 -> 验收矩阵
       -> 版本审查 -> Markdown/JSON/ZIP/交接提示词
```

每个阶段都必须保留来源和版本。用户可以追问一个章节、重新生成一个章节，不能因为修改局部内容而丢失其它已确认章节。

## 方案内容合同

### 需求方案

- 背景、目标用户、成功指标和非目标。
- 用户故事、主流程、异常流程和边界条件。
- 依赖、风险、权限和数据隐私假设。
- 可验证的验收条件，避免“体验更好”这类不可测试表述。

### 代码研发方案

- 基于已接入仓库的目录、模块、现有 API 和数据模型事实。
- 影响文件和模块边界，新增/修改/删除的理由。
- API 契约、数据库迁移、兼容策略、幂等和回滚。
- 租户、用户、权限、密钥、审计和外部网络边界。
- 测试层级：单元、集成、端到端、回归、性能和安全。
- 发布顺序、feature flag、灰度、监控指标和故障恢复。

### 任务与验收

每个任务必须包含：目标、前置依赖、涉及文件、实施步骤、风险、测试命令和验收证据。任务状态只描述事实，不把“模型生成完成”当作“代码验证通过”。

## 真实仓库事实规则

没有绑定仓库时，AOS 只能产出与仓库无关的需求方案，并必须明确标记“未完成代码事实核验”。绑定仓库后，方案需要引用扫描到的文件/模块；读取失败、分支不存在或仓库未同步时，必须把缺口列为阻塞项，不能编造路径。

## 外部 Code Agent 交接

方案详情提供：

- Markdown：适合人工审查。
- JSON：保留阶段、任务、验收和版本信息，便于自动化消费。
- ZIP：包含 `requirements.md`、`engineering-plan.md`、`tasks.md`、`acceptance.md`、`handoff.md` 和 `manifest.json`。
- 交接提示词：要求外部 Agent 先审查仓库事实，再按任务清单实施，最后运行验收矩阵。

交接文件不包含 API Key、数据库密码、Bot token 或本地绝对路径中的秘密。方案只引用凭据名称和配置入口。

## 与 Kiro Spec 的差异目标

AOS 不以模板数量取胜，而以可交付性取胜：

1. Kiro 风格的需求、设计、任务阶段全部持久化，并且每一段能追溯到原始需求和仓库事实。
2. 把租户权限、数据源治理、外部 Bot、审计、安全和回滚作为一等设计内容，而不是实施后再补。
3. 验收矩阵直接绑定测试命令、预期证据和风险，不只输出文本清单。
4. 支持局部追问和版本对比，避免一次生成后只能整篇重写。
5. 输出可被多个外部 Code Agent 消费，不锁定某个 IDE 或厂商。

## 菜单边界

- `代码仓库`：保留，负责接入、同步、分支和事实浏览。
- `规格驱动`：唯一研发主流程，负责需求与代码研发方案、审查、交付包。
- `研发配置`：只保留`团队规范`，作为方案和交接提示词的组织级约束。
- `代码开发`、`代码任务`、`质量快照`、Agent/Workflow 市场、Coding Agent、外部集成和 Hooks：第一阶段不出现在主导航；后端 API 和数据表保留，为未来受控执行能力留接口。

## 开源验收

- 新人只配置 API Key 和可选代码仓库即可生成第一版方案。
- 没有仓库时，页面清楚显示限制，不产生虚构文件路径。
- 每个阶段可查看、追问、批准和下载。
- 刷新页面、重新登录、切换租户后版本和交付物不丢失。
- 下载包可直接交给外部 Code Agent，且不含秘密。
- 任意失败都显示可操作原因和恢复动作，而不是“生成失败”泛化错误。
