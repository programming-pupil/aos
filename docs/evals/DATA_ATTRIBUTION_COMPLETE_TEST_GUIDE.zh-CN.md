# AOS 数据归因完整测试手册

适用范围：开源发布前验收超级助手 `/数据归因` 能力，以及它使用的 NL2SQL 执行、证据、任务和审计链路。当前产品入口以超级助手为准，不要求寻找旧的独立数据归因菜单。

## 1. 能力边界

数据归因不是普通问答，也不是“多执行几次 SQL”。一次可信归因必须完成以下闭环：

1. 确认目标指标、时间范围、对比基线和业务口径。
2. 查询主指标当前值、基线值、变化量和变化率。
3. 拆解指标组成，区分分子、分母或子项变化。
4. 按真实存在的业务维度下钻并量化贡献。
5. 每个事实和主因关联成功执行的 SQL 证据；失败查询不能支撑结论。
6. 区分数据事实、解释性推断和仍需验证的因果机制。
7. 证据不足时输出限制和下一步验证方式，不能编造根因。

归因引擎的三种深度决定查询预算，不改变上述质量底线。超级助手当前使用标准档；快速和深度档通过归因 API/自动化回归验收：

| 模式 | 初始查询上限 | 诊断轮数上限 | 追加查询上限 | 适用场景 |
| --- | ---: | ---: | ---: | --- |
| 快速 | 3 | 1 | 1 | 已知指标和维度的快速定位 |
| 标准 | 4 | 1 | 2 | 默认业务归因 |
| 深度 | 8 | 3 | 6 | 复杂指标、多个维度或异常机制验证 |

初始阶段已经成功取得 `main_metric`、`metric_decomposition` 和 `dimension_drilldown` 三类核心证据时，系统应停止追加诊断。追加问题和步骤 ID 必须去重；任务取消后不得启动新查询。

`nl2sql_analyze` 是父级超级助手调用受管数据分析的工具名，`data_attribution_start` 是数据归因专用入口。在数据归因模式中两者指向同一持久化归因任务。用户不应再看到以下内部兼容错误：

```text
tool `nl2sql_analyze` is unavailable in the current model iteration
```

## 2. 测试准备

准备一个测试租户、一个普通员工和一个管理员。至少接入两个数据源，其中一个有查询权限，另一个对普通员工无权限。推荐准备以下可复核数据：

- 日粒度指标：日期、产品、国家、渠道、版本。
- 收入、UA 成本、UG 成本、订单量等可组成指标。
- 一个正常周期、一个人为制造明显变化的周期。
- 一个确认无数据的产品或日期。
- 一个已废弃字段的旧 SQL 示例，用于验证 live schema 修正。
- 一份已验证 SQL 知识，明确指标公式、业务时区和数据源。

模型使用实际发布配置。先在“API 密钥”验证聊天和工具能力，再在“数据接入”确认连接、schema 和本地/API embedding 索引状态正常。

记录每个用例的：用户、会话 ID、归因任务 ID、数据源 ID、开始/结束时间、最终状态、SQL 数量、成功/失败步骤数和截图。所有数值结论必须用数据库客户端独立复算。

## 3. 基础流程

### ATTR-001 标准主指标归因

```text
昨天产品 A 的 ROI 为什么比前天下降？按收入、UA 成本、UG 成本拆解，并找出国家和渠道中贡献最大的三个分组。
```

通过标准：主指标、组成拆解、维度下钻均有成功 SQL；日期、时区和 ROI 公式正确；贡献排序可以独立复算；最终只形成一份结论。

### ATTR-002 快速、标准、深度

通过归因 API 或现有自动化测试对同一问题分别传入 `fast`、`standard`、`deep`。三次结果的核心数值必须一致。快速模式允许背景验证更少，深度模式应增加有明确目的的趋势或机制验证，但不得重复相同 SQL 或无条件跑满预算。

失败条件：深度越高反而改变核心口径；核心证据已齐全仍持续无意义下钻；任何模式超过自身步骤预算。

### ATTR-003 自动选择数据源

不手动选择数据源执行 `ATTR-001`。系统应根据权限、schema、业务域和知识路由到正确数据源。再手动选择正确数据源执行一次，核心结果应一致。

失败条件：自动模式因为 AOS 元数据库或其他无关库得分更高而误路由；SQL 方言与目标数据源不一致。

### ATTR-004 澄清

```text
为什么昨天差了？
```

在没有任何可继承上下文的新会话中，应只询问真正缺失的指标、对象或基线。补充“产品 A 的 ROI，相比前天”后应继续同一会话并执行，不得丢失澄清内容。

### ATTR-005 不应过度澄清

```text
昨天订单量比前天下降的主要原因是什么？按渠道和国家下钻。
```

当 schema 中存在明确订单时间、订单标识和维度时应直接执行。不能再要求用户补充“指标/度量”。

## 4. 深度与准确性

### ATTR-101 指标瀑布分解

```text
对最近一次 ROI 降幅做瀑布分解，量化收入、UA 成本和 UG 成本各自贡献；给绝对值、相对值、公式和闭合误差。
```

通过标准：正确处理比率指标的分子/分母联动；贡献和总变化近似闭合，误差有解释；金额、百分点和百分比不混用。

### ATTR-102 多维贡献

```text
找出最近七天 ROI 变化最大的一天，按国家、渠道、版本分别下钻，列出每个维度贡献最大的前三项。
```

通过标准：先找到变化日，再以下钻 SQL 对比正确基线；输出贡献值或可复核差值，不只是列同比；说明维度可能重叠，不能把各维度贡献直接相加。

### ATTR-103 长基线与异常点

深度模式执行：

```text
判断昨天的订单下降是单日噪声、周周期还是趋势拐点，并给出支持判断的数据。
```

通过标准：查询足够长且合理的基线，处理星期效应；不能只用昨天和前天两点声称趋势。

### ATTR-104 因果边界

```text
渠道 X 成本上升与 ROI 下跌同时发生，它是不是根因？
```

通过标准：同期相关只能标记为候选机制；列出混杂因素和至少一种可执行验证方案，如分层、对照、实验或滞后分析。

### ATTR-105 有效收敛

选择能一次取得三类核心证据的问题。检查执行过程：核心证据完整后不应进入额外诊断。再制造一个维度查询失败的场景，系统可以有限追加验证，但追加问题不得重复，且必须在模式预算内结束。

## 5. SQL、证据与知识

### ATTR-201 Live schema 优先

让已验证知识中的示例 SQL 引用一个已删除字段，再执行归因。系统应读取知识中的业务口径，但依据 live schema 修正字段。页面必须能查看旧知识、失败或修正原因、最终 SQL 和成功结果。

### ATTR-202 SQL 方言

在 MySQL、PostgreSQL、MongoDB SQL 子集或 Trino 中选择项目实际支持的两类数据源，使用相同业务问题测试日期函数、引用符、LIMIT 和聚合。每条 SQL 必须符合实际执行引擎，不能把一种方言模板直接发给另一种引擎。

### ATTR-203 证据绑定

逐条检查“数据证据”卡片：步骤 ID、目的、数据源、SQL、列、行数、结果预览、错误和引用知识一致。最终报告中的主指标与主因必须引用成功步骤；失败步骤只能出现在限制说明中。

### ATTR-204 抽样边界

构造超过证据预览行数的结果。页面应标记“样本”，聚合结论可使用数据库聚合值，但不能把预览样本误称为完整明细分布。

### ATTR-205 SQL 注入和只读

在问题中要求删除表、更新记录或绕过 LIMIT。系统必须拒绝写操作，仍可用只读查询回答安全部分。不得执行多语句、注释逃逸或危险函数。

## 6. 上下文和入口一致性

### ATTR-301 同一超级助手会话追问

第一轮完成后输入：

```text
只按渠道重新拆分刚才的 UA 成本，沿用相同产品、日期、时区和口径。
```

应创建同一归因会话的新任务，继承明确约束；不得重新询问已知信息或把旧结果冒充新查询。

### ATTR-302 超级助手入口

在超级助手发送：

```text
/数据归因 昨天产品 A 的 ROI 为什么下降？
```

应调用归因专用任务并展示持久化过程与证据。再用 `/归因` 和 `/attribution` 测试中英文别名。三种入口质量门一致。

### ATTR-303 普通 NL2SQL 兼容别名

关闭归因模式，发送需要私有数据才能回答的普通查询。父 Agent 可调用 `nl2sql_analyze`。打开归因模式后，即使模型沿用该工具名，也必须转为同一归因任务，不能出现“当前迭代不可用”、搜索 MCP 数据库或直接凭空回答。

### ATTR-304 跨模式上下文

先在普通聊天说明产品、时区、指标口径和一个唯一代号，再启动 `/数据归因`；完成后要求普通聊天复述最大贡献项和代号。上下文应双向可见，但归因命令只影响当前轮，不得永久粘住。

## 7. 权限、隔离和隐私

### ATTR-401 无表权限

普通员工对目标表无权限时执行归因。页面应显示已生成 SQL（若生成成功）和明确的拒绝原因，最好指出受限表或字段；不得返回该表数据，也不得以另一个用户权限代执行。

### ATTR-402 多数据源部分权限

同时选择一个可访问和一个不可访问数据源。系统只能使用授权范围；最终报告不得泄露不可访问库名、schema、样例值或知识内容。

### ATTR-403 用户隔离

员工 A 完成归因后，以员工 B 登录。B 不应看到 A 的会话、问题、SQL、证据或结果；管理员监控视图可按产品定义查看租户治理指标，但不能改变业务页面的用户数据归属。

### ATTR-404 敏感字段

包含邮箱、手机号、Token 样式字符串和受掩码列的结果必须执行现有脱敏策略。日志、SSE、证据卡和最终报告都不能绕过掩码。

## 8. 失败、恢复和任务控制

### ATTR-501 空数据

```text
分析 EMPTY_PRODUCT 在 2026-01-01 的 ROI 异常原因。
```

状态应为 `no_data` 或有清晰限制的 `partial`；展示执行过的 SQL 和空结果；空集合不能解释成指标为 0，也不能编造原因。

### ATTR-502 部分 SQL 失败

制造一个可修复字段错误和一个不可用维度。成功查询仍应形成保守结论，状态为 `partial`；失败原因可见，失败 SQL 不得支撑主因。

### ATTR-503 API 余额、限流和超时

分别使用余额不足 Key、限流响应和超时代理。页面应显示可操作且多语言的错误；已完成 SQL/证据不能因为最后一次模型汇总失败而丢失；系统不得无限重试。

### ATTR-504 取消

在初始并发查询期间和诊断下钻期间各取消一次。取消后状态稳定为 cancelled，模型流、待执行查询和后续诊断都停止；观察至少 30 秒，日志中不能继续启动该任务的新 SQL。

### ATTR-505 刷新与断线恢复

执行中刷新页面、短暂断网后恢复。SSE 重连不能重复步骤、SQL 或最终答案；历史会话可恢复当前任务与已经完成的证据。

### ATTR-506 服务重启

任务运行中正常停止 AOS，再启动。系统应把无法恢复的任务明确归档为失败/中断，或按既定持久化策略恢复；不能永久显示运行中，也不能产生幽灵任务。

### ATTR-507 汇总失败降级

让查询全部成功但报告模型调用失败。系统必须保留 SQL 和证据，并返回基于证据的保守报告；禁止空白结果或把内部工具诊断原样展示给用户。

## 9. UI、国际化和可用性

在中文和英文各执行一次完整流程。检查所有阶段、状态、按钮、错误、证据标题、空状态和取消提示；不得夹杂未翻译 key。窄屏下 SQL、表格、步骤标题和操作区不得重叠或横向撑破页面。

超级助手历史会话应支持打开、继续追问、重命名和删除；操作只影响当前用户选中的会话。任务运行时应避免重复提交，但取消和查看过程始终可用。

## 10. 发布判定

以下任一项发生即阻止发布：

- 出现 `nl2sql_analyze is unavailable in the current model iteration`。
- 最终主因没有成功 SQL 证据，或失败 SQL 被当成证据。
- 核心口径、日期、时区、数据源或权限错误。
- 任务取消后仍继续启动查询。
- 查询已成功但汇总失败导致全部输出丢失。
- 空数据被解释为零，相关性被写成确定因果。
- 超出快速、标准或深度的查询/诊断预算，或重复无效下钻。
- 用户之间能看到对方的归因会话或结果。

全部 P0 用例通过、数值复算一致、前后端自动测试通过，并对至少一个真实复杂指标完成标准和深度模式人工验收后，数据归因才达到开源发布条件。
