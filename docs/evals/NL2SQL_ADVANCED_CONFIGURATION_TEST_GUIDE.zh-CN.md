# NL2SQL 高级配置说明与完整测试手册

本文对应 WebUI `高级配置`（`/nl2sql/management`）的当前实现，用于从零理解并验收全部 10 个页签。测试结论必须来自真实数据探索查询、生成 SQL、执行结果和规则命中记录，不能只验证“页面保存成功”。

## 1. 测试基线

### 1.1 前置条件

- 使用一个全新租户，并准备管理员账号和普通成员账号各一个。
- 至少接入两个可查询数据源；单数据源应包含 3 张以上有业务关系的表。
- 完成 Schema 发现与语义索引，数据探索可以生成并执行基础 SQL。
- 测试表应包含日期、金额、状态、用户标识、邮箱或手机号等字段，并准备可核对的固定数据。
- 记录每次测试的问题、生成 SQL、结果、规则命中、账号、数据源和执行时间。

### 1.2 每个页签的通用检查

- 创建、读取、编辑、删除后刷新页面，状态必须与保存结果一致；提供启用/停用状态的页签还要验证状态切换。
- 非法必填项、重复配置、错误表名/列名必须被拒绝或给出明确错误，不能静默保存。
- 租户 A 的配置不能被租户 B 查看、修改或用于查询。
- 普通成员不能绕过菜单权限直接调用管理接口修改配置。
- 配置命中时，在数据探索结果的“规则命中”或对应审计信息中能看到证据；未命中时不能伪造命中记录。
- 删除配置后，用相同问题复测，影响应消失；支持启用状态的规则还要验证停用后消失、重新启用后恢复。

## 2. 页签总览

| 页签 | 解决的问题 | 主要作用范围 | 是否通常必配 |
| --- | --- | --- | --- |
| 业务域 | 哪些表属于同一业务主题 | 单数据源路由与 SQL 表范围 | 大 Schema 推荐 |
| 同义词 | 用户说法与物理字段不一致 | 单数据源召回、表列匹配 | 强烈推荐 |
| 指标 | 统一“收入、订单量”等口径 | SQL 表达式、过滤和粒度 | 核心指标推荐 |
| 时间模式 | 统一“本周、财年”等时间说法 | Query Understanding 时间解析 | 有自定义时间口径时 |
| 校验规则 | 结果是否超范围、过期或异常 | SQL 执行后的结果质量 | 关键报表推荐 |
| 跨数据源关联 | 两个数据源如何合并 | 多数据源规划与 MERGE 校验 | 仅跨源查询需要 |
| 跨域聚类 | 哪些数据源属于同一跨域主题 | 多数据源规划提示 | 多数据源场景推荐 |
| 查询权限 | 某用户能查哪些表、列和行 | SQL 生成后的强制安全检查 | 多用户部署推荐 |
| 关系建模 | 表之间怎样 JOIN | SQL 生成提示与 Join Path | 缺少数据库外键时推荐 |
| 列脱敏 | 敏感结果如何展示 | SQL 结果返回前脱敏 | 生产数据推荐 |

## 3. 业务域

### 3.1 是什么、如何生成

业务域是在一个数据源内把相关表分组，例如“订单履约”包含订单、订单明细和物流表。点击“重新发现”后，后端读取当前 Schema 的表名、列名和描述，由 LLM 生成候选分组，再校验表名、去重并保存；也可以手工创建业务域并分配表。

路由模式有两种：

- `软引导（assist）`：命中域后提高域内表的候选权重，但不排除域外表。适合域边界可能交叉的默认场景。
- `强过滤（strict）`：当问题明确命中该域时，只把域内表交给 SQL 生成器，并在 SQL 生成后再次检查实际引用表。适合边界稳定、误查域外表风险较高的场景。

强过滤不是“该数据源永远只能查这些表”。只有问题命中严格业务域时才收窄表范围；未命中时仍按正常路由工作。

### 3.2 从零测试

1. 选择数据源，点击“重新发现”，确认任务完成且每个生成域至少包含一张真实表。
2. 检查自动生成的名称、描述、置信度、表数量和实际表清单；任何不存在的表都属于失败。
3. 创建“订单履约测试域”，分配订单表与明细表，设为软引导。
4. 在数据探索提问一个同时可能命中订单表和其他表的问题，确认域内表优先但系统仍可选择必要的域外表。
5. 将同一域改为强过滤，提出明确包含域名称或域描述语义的问题，确认 SQL 只引用域内表，并出现 `strict_domain_filter` 规则证据。
6. 设计一个必须使用域外表才能回答的问题。明确命中严格域时，系统应拒绝引用域外表或要求澄清，不能偷偷放宽；若生成器产出域外表，应由 `strict_domain_sql_blocked` 阻断。
7. 提出一个完全不命中该域的问题，确认强过滤不会错误限制其他业务查询。
8. 编辑表映射、删除一个域内表并复测；再删除业务域，确认限制立即消失。

## 4. 同义词

### 4.1 是什么

同义词把业务说法映射到真实表或列，例如“会员号”映射到 `users.member_id`。它用于补足物理命名、缩写、中文口径和用户习惯之间的差异，提高路由与字段召回，不直接写死最终 SQL。

### 4.2 从零测试

1. 选择数据源，创建一个数据库中不存在但业务人员常用的词，映射到真实表和列。
2. 使用该词提问，确认生成 SQL 使用映射后的表/列，并出现 `synonym_resolved` 证据。
3. 使用原始列名提出等价问题，结果应与同义词问题一致。
4. 创建表级和列级同义词各一条，验证两种类型均生效。
5. 导出 CSV，检查字段完整；修改 CSV 后批量导入，验证成功数、失败行和重复项提示准确。
6. 将同义词映射到不存在的表/列，页面或接口应拒绝；若 Schema 后续删除目标列，查询不得生成不存在字段。
7. 删除同义词并重复原问题，`synonym_resolved` 不应继续出现。

## 5. 指标

### 5.1 是什么

指标保存统一业务口径：指标名称、别名、SQL 表达式、固定过滤条件、默认粒度和说明。例如“有效收入”可定义为金额求和并排除取消状态。指标经过 `草稿 -> 审核中 -> 已批准` 流程，只有可用状态的定义才应成为权威口径。

### 5.2 从零测试

1. 选择数据源，创建一个测试指标，表达式使用真实金额列，添加状态过滤、别名和默认日粒度。
2. 在草稿状态用指标名提问，记录是否被采用；提交审核并批准后再次查询，批准后的口径必须稳定命中。
3. 使用指标名称和别名分别提问，SQL 表达式、固定过滤条件和结果应一致，并出现 `metric_resolved`。
4. 将测试数据手工计算出期望值，与查询结果核对。
5. 提问“按周/按月”时，用户明确指定的粒度应覆盖默认粒度；未指定时使用指标默认粒度。
6. 驳回一个待审核指标，确认它不会冒充已批准指标被使用。
7. 测试空表达式、危险 SQL、未知列和重复指标名，必须被校验，不能生成可执行的错误口径。
8. 编辑已使用指标后复测，并核对历史查询不会被无提示地改写。

## 6. 时间模式

### 6.1 是什么

时间模式把自然语言时间表达式的正则规则映射为标准时间类型、粒度、偏移和优先级。它在 Query Understanding 阶段解析时间范围，适合“财年、本结算周、上个账期”等默认规则覆盖不到的口径。

### 6.2 从零测试

1. 创建一个只匹配测试短语的时间正则，选择解析类型、粒度、偏移和优先级。
2. 在数据探索使用该短语，检查“查询理解”的时间范围与预期日期完全一致，并出现时间规则命中证据。
3. 使用一个不匹配的近似短语，规则不得误命中。
4. 创建两个都能匹配的规则，设置不同优先级，确认只采用高优先级结果。
5. 测试无效正则、极端偏移、月末、年末、闰日和时区边界。
6. 停用规则后相同短语不得继续使用旧缓存结果；重新启用后恢复。

## 7. 校验规则

### 7.1 是什么

校验规则在 SQL 执行并取得结果后检查质量，不改变原始数据。当前支持范围、空值比例、行数、新鲜度和基数等规则，用于发现明显异常结果并展示告警或建议。

### 7.2 从零测试

1. 为固定测试列分别创建 `range`、`null_ratio`、`row_count`、`freshness`、`cardinality` 规则。
2. 准备一组通过规则的数据，执行覆盖目标列的查询，确认无误报警。
3. 准备或筛选出违反每条规则的数据，确认结果面板显示正确规则、严重性和实际值。
4. 查询不包含目标列时，该列规则不得误报。
5. 验证边界值：等于最小/最大值、空结果、全空列、单行、重复值和过期时间。
6. 停用一条规则后复测，只有该规则的告警消失；其他规则不受影响。
7. 关闭结果校验的部署配置时，页面应明确没有执行校验，不能把“未执行”显示成“通过”。

## 8. 跨数据源关联

### 8.1 是什么

跨数据源关联声明两个数据源中可以匹配的表和列及匹配类型。多源规划器用它规划合并步骤，并检查 MERGE 是否使用已知关联键；它不会在单个数据库里创建真实外键。

### 8.2 从零测试

1. 在两个数据源准备可核对的共同键，创建左右数据源、表、列和匹配类型。
2. 提出必须跨两个数据源回答的问题，确认生成多源计划、分别执行查询并按配置键合并。
3. 手工核对匹配行、未匹配行、重复键和空键的结果。
4. 交换左右数据源后验证语义仍正确；测试一对一、一对多或当前页面支持的不同匹配类型。
5. 使用未登记的列要求跨源合并，系统应提示合并质量风险，不能伪造“已配置关联”。
6. 删除关联后复测，计划不得继续声称命中该关联。

## 9. 跨域聚类

### 9.1 是什么

跨域聚类把多个数据源归入同一个更高层业务主题，为多数据源 Agent 提供规划提示。例如“客户全景”可包含 CRM 与交易数据源。它是软规划上下文，不是权限边界，也不替代具体的跨数据源关联键。

### 9.2 从零测试

1. 创建聚类名称、描述并选择两个数据源。
2. 用描述中的业务概念提出跨源问题，确认规划优先考虑聚类成员，而不是无关数据源。
3. 提出只涉及其中一个数据源的问题，不应为了“凑跨源”强行执行另一个数据源。
4. 提出涉及聚类外数据源的问题，系统仍可在证据充分时选择它，不能把软提示当强过滤。
5. 编辑成员列表、删除聚类并复测，规划上下文应随之变化。

## 10. 查询权限

### 10.1 是什么

查询权限按“用户 + 数据源”定义允许/拒绝的表、列和行过滤表达式。它在 SQL 生成后、执行前做强制检查。拒绝项优先于允许项，不能依靠模型自觉遵守。

### 10.2 从零测试

1. 为普通成员和测试数据源创建策略，仅允许一张表并拒绝其中一个敏感列。
2. 使用该成员查询允许表，确认成功并出现 `query_policy_applied`。
3. 查询拒绝表、拒绝列，以及通过别名、子查询、JOIN、大小写或限定名绕过，均必须被阻断。
4. 设置行过滤表达式，查询全量数据，确认最终 SQL 或执行结果始终受行过滤约束。
5. 测试 `SELECT *`，不得借此返回拒绝列。
6. 管理员和另一普通成员应按各自策略工作，不能共享错误策略。
7. 停用或删除策略后再测试，并确认变更只影响目标用户和数据源。

## 11. 关系建模

### 11.1 是什么

关系建模包含两个子页签：

- 外键定义：补充数据库 Schema 中不存在或无法读取的源表、源列、目标表、目标列及类型关系。
- Join Path：保存可复用的多跳关联路径和 SQL JOIN 片段，帮助复杂查询选择稳定路径。

### 11.2 从零测试

1. 为两张没有物理外键但数据上可关联的表创建手工外键，确认表列和类型均来自当前 Schema。
2. 提出需要 JOIN 的问题，确认 SQL 使用正确关联列，并出现 `manual_foreign_keys_loaded`。
3. 创建包含两跳以上的 Join Path，设置路径文字、JOIN SQL 和跳数；复测复杂查询并确认 `join_paths_loaded`。
4. 用固定数据核对 JOIN 后行数，重点检查一对多导致的金额重复累加。
5. 创建类型不兼容、循环、未知表列或危险 JOIN SQL，必须被拒绝或明确告警。
6. 删除 Join Path 后，系统可重新规划，但不得继续显示已加载该路径。

## 12. 列脱敏

### 12.1 是什么

列脱敏在结果返回 WebUI 前处理敏感值。规则可指定数据源、表、列、脱敏类型、常量、优先级和启用状态。当前类型包括 `redact`、`null`、`constant`、`hash`、`tokenize`、`partial`。

### 12.2 从零测试

1. 为邮箱或手机号列逐一创建不同脱敏类型，执行直接查询并检查返回值。
2. 验证相同原值在需要稳定映射的模式下结果稳定，不同原值不会错误合并。
3. 测试列别名、限定名、JOIN、分页、导出、图表和历史结果加载，任何入口都不能泄漏原值。
4. 创建数据源专属规则与租户通用规则，验证优先级和作用范围。
5. 测试大小写列名、空值、短字符串、Unicode 和超长值。
6. 停用规则后仅在明确授权的测试账号下确认原值恢复；随后立即重新启用。
7. 浏览器网络响应和后端日志中也不得出现未脱敏的结果数据。

## 13. 组合场景

单项通过后必须做组合测试，避免配置之间互相覆盖：

1. `同义词 + 指标 + 时间模式`：用业务别名询问自定义账期指标，三种规则均命中且结果口径正确。
2. `严格业务域 + 查询权限`：业务域允许但用户策略拒绝的表必须拒绝，权限优先。
3. `关系建模 + 指标`：跨表计算指标时 JOIN 不得造成重复聚合。
4. `跨域聚类 + 跨数据源关联`：聚类帮助选源，关联定义负责合并，两者证据不能混淆。
5. `查询权限 + 列脱敏`：有权查询但需脱敏的列返回脱敏值；无权查询的列直接阻断，不能只靠脱敏放行。
6. `校验规则 + 列脱敏`：质量校验应针对正确数据语义执行，最终对用户展示的数据仍必须脱敏。

## 14. 发布验收标准

- 10 个页签全部完成正向、负向、边界和租户隔离测试；支持启用状态的规则还须完成停用/恢复测试。
- 所有强制安全能力在后端执行，绕过 WebUI 直接调用接口也不能失效。
- 所有软引导能力只影响排序或规划，不会无证据地排除正确数据源和表。
- 每个命中结果都有可核对的规则或审计证据，页面计数与实际查询一致。
- 任何失败都给出用户可执行的修复提示，不出现无限加载、静默降级或成功假象。
- 所有测试问题、SQL、结果和截图归档后，才可在发布清单中将高级配置标记为通过。
